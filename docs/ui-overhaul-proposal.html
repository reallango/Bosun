Bosun UI overhaul

What feels unpolished today, the options, a recommendation for each, and a phased plan. The prototype on branch prototype/ui-overhaul already does the recommended widget-size and layout work (sections 3 and 4).

Written against dev at ff86bdd. Every file path below is relative to the repo root.

The short version
  1. Fix layouts first. Today, arranging a dashboard on one screen size does nothing for the others. Make one base layout that follows your last edit, with per-size overrides on top and a "Use on all sizes" button. prototyped
  2. Give every widget a size class (xs/sm/md/lg, measured on the widget, not the screen). Add generic spec keys (hideBelow, row.inline) so a package decides what drops out on small tiles. Row actions that do not fit go into a ⋯ menu. prototyped
  3. One look for the widget system. Move the declarative renderer, its dialogs and its menus onto the theme tokens and ui/* primitives the shell already uses. Today the two halves look like different apps.
  4. Navigation. Turn the settings accordion into a real settings area with its own grouped sub-navigation. Polish the server list (status, hostname, tooltips, a proper mobile sheet).

1. Sidebar and settings menu

What is wrong today

  • Settings is an accordion inside the sidebar. src/components/layout/Sidebar.tsx (around line 372) expands 14 links upward above the Settings button, capped at max-h-[50vh].
    • There is no settings/layout.tsx, so there is no in-page navigation.
    • The accordion is closed on every page load, even while you are on a settings page.
    • The active state there is just white text, not the bg-sidebar-accent every other item uses.
    • The chevron is inverted.
  • Inconsistent settings pages. Widths alternate between max-w-4xl/5xl/6xl. Titles mix cases ("Access requests" vs "Alert Rules"; the sidebar says "Alerts").
    • Section headings are sometimes a Card and sometimes a bare <h2> (Permissions, Widgets).
    • Save buttons and "Saving…" states are hand-written per form.
    • widgets/page.tsx uses window.confirm.
  • The server list is thin. It has a name and a dot with hard-coded bg-green-500/yellow-500/gray-500, although success/warning tokens exist.
    • There is no hostname, no hover detail, no grouping or sorting, and no empty state.
    • When the rail is collapsed, servers become two-letter initials, and labels rely on the native title= attribute (there is no Tooltip primitive).
  • The mobile drawer is a raw radix Dialog with no slide animation, and it repeats the settings accordion.
  • Small things.
    • "SSH Keys" and "Access Requests" share the KeyRound icon.
    • The collapse toggle jumps between the header and its own bar.
    • Dashboards can only be reordered with up/down chevrons, in a separate edit mode.

Options

A. Polish in placeKeep the accordion. Fix the active state, the chevrons and the tokens, add tooltips, and make the drawer animate.Small (1–2 days). Still crams 14 links into the sidebar, and settings still has no structure.
B. Settings becomes its own area (recommended)The sidebar keeps one "Settings" link. settings/layout.tsx adds grouped sub-navigation:
  • You: Account, SSH keys
  • Servers: Servers, Cluster, Alerts
  • Access: Users, Groups/Permissions, API access, Access requests
  • System: General, Widgets, Updates, Database, Audit log
The sub-navigation is a left column on desktop and a horizontal scroller or select on phones. It adds a shared PageHeader and SettingsSection (title, description, body, footer with the save button). C. Command palette on top⌘K / Ctrl+K to jump to any server, dashboard or setting.Additive; a good follow-up to B rather than a replacement. Needs a cmdk-style dependency or about 200 lines of our own.

  • In the same pass, polish the server list:
    • status dot from tokens with a real role="img" label
    • hostname as a second line in the expanded rail
    • a hover card with CPU, memory and last seen
    • sorted with offline servers first, and an "Add server" empty state
  • Add a Tooltip primitive (radix is already installed) for the collapsed rail.
  • Add a Sheet primitive for the mobile drawer.

2. The widget screen and menu system

What is wrong today

The shell (sidebar, header, src/components/ui/*) uses theme tokens. The declarative widget system does not, so it looks like a second app.

  • Hard-coded colours. LayoutView.tsx has about 76 hard-coded gray-*/blue-* classes, EditorBlock.tsx about 70 and DeclarativeWidget.tsx about 33. In light mode the theme is slate, so these grays visibly clash. inputClass and buttonClass are copy-pasted between LayoutView.tsx and EditorBlock.tsx.
  • Three dialog styles.
    • ScreenDialog.tsx and widgets/shared/ConfirmActionDialog.tsx are raw radix with their own sizes (max-w-lg/3xl/5xl).
    • ui/dialog.tsx uses a different scale.
    • dialogs/DeleteConfirmDialog.tsx is a third style, so the app has two confirm dialogs.
    • Screens have no footer slot, so submit buttons float inside the blocks.
  • Row actions are a strip of tiny gray icons (IconBtn in parts.tsx: p-1, 14 px).
    • The Docker list shows up to six per row, and on a narrow tile they push the container name down to an ellipsis.
    • There is no overflow menu.
    • Every button greys out while any action runs.
  • The frame ⋮ menu (WidgetFrame.tsx) mixes the package's entries (New container, New stack, Manage) with Refresh, Settings and Remove. Only a separator tells them apart.
  • Hand-rolled tabs and sections in LayoutView.tsx. Tabs have role="tab" but no arrow-key support, and the active tab is blue-500 rather than primary.
  • Feedback is a dismissible notice string inside the widget (useActionRunner.tsx), although ui/toast exists.
  • Full-page screens (ScreenPage.tsx) have a "Back to the dashboard" text link, and the breadcrumb shows a raw /widgets/<id>.

Options

OptionWhatTrade-offs
A. Re-skin onlySearch and replace gray-* with tokens (text-muted-foreground, border-border, bg-muted). Share inputClass and buttonClass.1–2 days. It fixes the clash but not the structure (dialog sizes, footers, overflow).
B. Renderer on ui/* primitives (recommended)
  • Add the missing primitives: Tabs, Select, Badge, Tooltip, Callout, Collapsible, Skeleton.
  • Make ScreenDialog a ui/dialog with one size scale and a sticky footer, where an editor's submits render.
  • Merge ConfirmActionDialog into one ConfirmDialog.
  • Group the frame ⋮ menu by label: the package entries under the widget name, then "Widget" (Refresh, Settings, Remove).
  • Row actions: as many as fit, the rest in a ⋯ menu (already in the prototype).
  • Results go to toasts.
About 1 week. Every package gets it for free with no spec change, and the look matches the shell. The risk is visual regressions in the Docker editor screens, which need a manual pass.
C. Spec-level "menus"Let a spec declare grouped menus (menu: [{group, items}]), primary or secondary actions, and keyboard shortcuts.More power for authors, but more spec surface to support forever. Do it only when a second package needs it.
Recommendation: B.
  • It is core-only and generic, and old specs render with the new look unchanged.
  • Keep C in reserve.
  • Today's spec already has the information needed: actions order gives priority, and confirm.destructive marks danger. Destructive actions can therefore be sorted to the bottom of a ⋯ menu and shown in red without new keys.

3. Widget content that scales with widget size

What is wrong today

  • Widgets do not know how big they are.
    • WidgetFrame.tsx sets @container, but only the header uses it (the server chip at @[16rem]).
    • The declarative renderer (DeclarativeWidget.tsx, LayoutView.tsx, parts.tsx) renders the same blocks at 3 columns and at 24.
    • A few rules use the screen breakpoint (sm:inline for list badges, sm:max-w-[220px] for the filter). That is wrong inside a grid: a small tile on a big screen gets the big-screen treatment.
  • No way for a spec to say what matters.
    • A package cannot say "this column is optional", "the filter is not needed on a tiny tile" or "show two buttons, the rest in a menu".
    • when conditions only see data, never size.
  • Everything is text-xs and plain. There is no density step, no headline number for small tiles, and no skeleton loading.

Options

OptionWhatTrade-offs
A. Automatic onlyThe renderer adapts on its own: actions overflow into a menu, padding tightens, and badges hide on narrow tiles.No spec change, and old packages improve. But the renderer must guess what is important.
B. Size classes and hideBelow hints (recommended, prototyped)The frame measures its content box and assigns xs <280px, sm <420, md <640 or lg. Specs opt in with:
  • hideBelow on any v2 block, fields item, table column, summary entry, filter and toggle
  • row.inline (buttons per size)
  • row.subtitleHideBelow
Sensible defaults (A) apply when a spec says nothing.		Small, declarative and generic, and dialogs and pages always count as lg. Older servers ignore the unknown keys, because validators copy known keys only, so a package that uses them still installs there and shows everything.
C. Size variantsview.variants: { xs: {…view…}, md: {…} }: a whole alternative view per size, for example a single headline number on xs and a full table on md.The most expressive option. Specs get longer, and two views must be kept in sync. Worth adding later for "stat tile" widgets, on top of B.
D. Density levelsA frame-level density: compact|comfortable, chosen per widget in its settings, that switches type scale and padding.Orthogonal to B. Cheap once the renderer uses tokens (section 2), so do it there.
Recommendation: B now, built on A's defaults; D with the re-skin; C when a "stat" widget needs it.
  • Size is measured on the widget, never the screen, so a 4-column tile behaves the same on a phone and on a 4K monitor.
  • The size context is a core React context (useWidgetSize()), so even a non-declarative widget can use it.

Rules for the spec keys

  • Small set. hideBelow accepts sm|md|lg only (xs would mean "never hidden", so it is rejected to catch typos). row.inline accepts 0–10 per size; a size that is left out takes the nearest smaller one. A ⋯ menu with a single entry is never made.
  • Validated like everything else (src/lib/widgets/runtime/size.ts, called from spec.ts and spec-v2.ts). A malformed hint fails the install with a message, as any other spec error would.
  • Still to add later:
    • a height class (short, for 2-row tiles, to drop summaries)
    • view.variants (option C)
    • a stat block (big number, label, trend, sparkline) so small tiles stop looking "basic"

4. Responsive dashboard layouts

What is wrong today

The grid (src/components/dashboard/DashboardGrid.tsx, react-grid-layout Responsive) has seven breakpoints, from xxl with 36 columns down to xxs with 2, measured on the container (src/lib/widget-sizes.ts). Storage is:

  • widgets.grid_*: the lg (24-column) layout.
  • widgets.layouts (JSON): per-breakpoint overrides.

Sizes that are not saved derive from lg: scaled sideways, and stacked on phones.

The flaw: an edit only touches the breakpoint you are on.

  • Arrange the dashboard on a big monitor (xl, 1600 px and wider) and only layouts.xl changes.
  • The laptop (lg), small laptop (md) and tablet (sm) keep deriving from the old lg layout, so they look unrelated to what you built.
  • Every screen size has to be arranged separately, and a widget added later lands in a different place on each.

That is exactly the "I can make it look decent for one layout, but when I change screens it doesn't lay out the same" report.

Options

OptionHow it worksTrade-offs
A. Independent layout per breakpoint (today)Each size is arranged on its own.Maximum control, but you arrange up to six times, and nothing carries over.
B. One ordered layout that reflowsStore only an order and a preferred size per widget. Pack them row by row (masonry or flow) for each column count.Zero per-size work, and phones are trivially correct. But you lose free 2-D placement (side columns, a tall widget next to two short ones), which people building home-lab walls do use. It also needs a new packer and a data migration.
C. One base layout that follows your last edit, plus overrides (recommended, prototyped)
  • grid_* becomes the base, in 24-column units.
  • An edit on any multi-column size saves that size's arrangement (layouts[bp]; layouts.lg for lg) and becomes the base, scaled to 24 columns.
  • Sizes you never arranged follow the base. Sizes you did arrange keep their own arrangement until you press Reset this size.
  • Use on all sizes makes the current arrangement the only one.
Keeps 2-D placement, needs no migration, and old data renders exactly as before. One subtlety: a laptop layout arranged before this change is not marked as its own, so it follows a later edit on another size. "Use on all sizes" and "Reset this size" make this explicit and recoverable.
Recommendation: C.
  • It matches how people actually work: arrange once on the main screen, and tweak the odd size if needed.
  • The edit bar says which size you are arranging and whether it follows the base or has its own arrangement.

The concrete questions

QuestionAnswer in the prototype
Per-breakpoint layouts or one that reflows?Both, layered. One base (reflows by scaling to each column count), with optional per-breakpoint overrides on top.
How do existing saved layouts migrate?No migration.
  • Without layouts.lg, lg shows grid_* as before.
  • Existing layouts.xl etc. stay as overrides.
  • The first edit on any size moves the base, and from then on the other sizes follow.
  • For a dashboard that was tuned on a big screen only, one click on Use on all sizes makes the laptop and tablet match.
The PATCH API stays backward compatible: a body without mode is an edit, and a body without breakpoint is lg.
What happens on a phone?Below 768 px of container width, widgets stack in one column, in the reading order of the base (top-to-bottom, then left-to-right). Height is clamped to 3–12 rows.
  • Drag and resize are off on touch phones, because they fight with scrolling.
  • Reordering for phones on a desktop browser (narrow window) is saved as a phone-only override and never moves the base.
  • Next step: a "Move up / Move down" item in the ⋮ menu so phones can reorder without dragging.
How does a widget declare min/preferred sizes?Already in the manifest: default_size (preferred, in base columns and rows) and min_size. They are copied to grid_min_w/h when the widget is added and scaled per breakpoint (scaleMin). Proposed additions:
  • max_size
  • phone_height (rows when stacked), so a terminal or chart is not clamped to 12 rows and a stat tile is not inflated to 3
The size classes of section 3 make content cope with whatever size results.

5. Keeping widgets self-contained

  • Generic only. Everything above is in generic core components: the frame, the renderer, the grid and the validators. No core file names a bundled widget, and guard-rails.test.ts still passes.
  • The package carries its own hints. They live in its manifest.json, so a widget is still imported from one file through the database transfer and update path.
  • Proposed: requires.bosun in the manifest. The manifest has a package version but no minimum server version today.
    • Add "requires": { "bosun": ">=1.4.0" }.
    • The installer refuses with "needs Bosun 1.4.0 or newer" instead of failing on a validator message.
    • Size hints do not strictly need it, because old servers ignore them. Features that change meaning (variants, new block types) do.
    • The check is about 30 lines in package-manifest.ts plus a test.
  • One house style. New spec keys follow the existing pattern: optional, validated, documented in widgets/README.md ("Widget sizes" section added in the prototype).

7. What the prototype changes

Branch prototype/ui-overhaul, off dev. There are no flags. Old dashboards and old specs keep working.

  • src/lib/widget-sizes.ts: the edit model (applyLayoutEdit, applyLayoutEverywhere, resetLayoutAt, toBaseRect). lg honours layouts.lg. Tests are in widget-sizes.test.ts.
  • src/app/api/dashboards/[dashboardId]/layout/route.ts: mode: edit | everywhere | reset, using the same pure functions. The legacy body is unchanged.
  • src/hooks/useDashboard.ts, DashboardGrid.tsx, DashboardView.tsx, and the new LayoutEditBar.tsx: the edit bar.
  • src/lib/widgets/runtime/size.ts (new, with tests): size classes, splitActions, and validators. spec.ts and spec-v2.ts accept hideBelow, row.inline and row.subtitleHideBelow.
  • src/components/dashboard/widget-size.ts (new): useWidgetSize() context. WidgetFrame.tsx measures the body and provides it, and ScreenDialog.tsx resets it to lg.
  • DeclarativeWidget.tsx, LayoutView.tsx, parts.tsx: honour the hints, and add the per-row ⋯ menu.
  • widgets/docker/manifest.json (1.0.13) and widgets/README.md: the hints and their documentation.
